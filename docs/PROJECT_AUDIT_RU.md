# Аудит проекта `insurance-comparator`

Дата аудита: 2026-10-05  
Ветка: `main`  
Репозиторий: `vilvetti-cloud/insurance-comparator`

## 1. Краткий вывод

Проект уже содержит значительное доменное ядро для сравнения КАСКО:

- сравнение двух страховых компаний по 10 параметрам;
- сбор данных с официальных сайтов и PDF-документов;
- приоритизация официальных правил;
- проверка точной цитаты, страницы, раздела, чисел и единиц измерения;
- карантин неподтверждённых AI-ответов вместо публикации сомнительных значений;
- ежедневная актуализация через GitHub Actions;
- PostgreSQL-модель с источниками, документами, версиями условий, доказательствами и журналом изменений;
- sales-first результат: преимущества, осторожные формулировки и готовая фраза для клиента;
- заготовка расширения на страхование недвижимости.

Главная продуктовая проблема: проект одновременно содержит два поколения приложения и несколько направлений развития. Поэтому сейчас он больше похож на сильный технический прототип/внутренний инструмент, чем на цельный продукт с одним очевидным пользовательским сценарием.

## 2. Что уже работает концептуально

### Основной пользовательский сценарий

В `web_app.py` реализован сценарий:

1. выбрать свою страховую компанию;
2. выбрать конкурента;
3. получить sales-first сравнение;
4. увидеть подтверждённые преимущества;
5. скопировать готовый текст для клиента;
6. раскрыть подробную таблицу по 10 параметрам;
7. открыть источник каждого значения;
8. перейти в отчёт качества данных.

Это хорошая основа для продукта **«помощник страхового агента»**.

### Данные и доказательность

`database/schema.sql` уже моделирует:

- компании и продукты;
- поля сравнения;
- источники и документы;
- условия и их версии;
- evidence-фрагменты с номером страницы;
- change log;
- запуски сбора и их результаты;
- версии документов КАСКО и кандидатов на ручную проверку.

`docs/casco-document-pipeline.md` описывает консервативную стратегию: неподтверждённое значение не должно автоматически попасть в активные условия. Для страхового продукта это сильное конкурентное преимущество, потому что снижает риск выдуманных или устаревших характеристик.

### Автоматизация

В `.github/workflows/` есть отдельные workflow для:

- ежедневной проверки и обработки документов;
- CI тестов CASCO;
- ручного review и repair;
- E2E по одному документу;
- пилота Т-Страхования;
- пилота недвижимости;
- аудита данных.

## 3. Ключевые найденные проблемы

### P0 — два веб-приложения и неоднозначный запуск

Есть старый контур `app.py` и новый нормализованный контур `web_app.py`.

- `vercel_db_entry.py` импортирует `web_app:app` — это текущий Vercel-контур.
- `vercel_entry.py` обходит старый `app.py` через monkey-patching импорта.
- `Procfile` всё ещё запускает `gunicorn app:app` — старый контур.
- В `app.py` остаётся старый web-scraping/Groq-сценарий и запуск обновления данных при импорте (`UPDATE_ON_START = True`).

Риск: разные среды могут запускать разные продукты, а исправления в одном контуре не попадут в другой. Это также затрудняет диагностику production-инцидентов.

**Рекомендация:** выбрать `web_app.py` единственным приложением, перевести `Procfile` на `vercel_db_entry:app` или отдельный чистый entrypoint, а `app.py` и `vercel_entry.py` убрать после миграционного периода.

### P0 — нет явного ответа, для кого продукт

Текущие формулировки («Подготовка к продаже», «Ваша страховая», «Аргументы для продажи») говорят об инструменте для агента/менеджера. При этом название репозитория и часть инфраструктуры допускают сценарий публичного сравнения страховок.

Нужно выбрать основной продукт:

1. **B2B-инструмент для страховых агентов** — приоритет продаж, история сравнений, CRM, роли, команды, экспорт и контроль доказательств.
2. **Публичный B2C-сервис** — подбор продукта клиентом, анкета автомобиля, расчёт/лид, партнёрская монетизация, юридические дисклеймеры.
3. **Гибрид** — публичная форма приводит лид, агент получает проверенное сравнение и sales script.

Без этого нельзя корректно выбрать UX, модель доступа, KPI и дальнейшие интеграции.

### P0 — текущий UI не использует весь потенциал данных

Результат уже показывает источники и статусы, но остаются важные продуктовые возможности:

- нет единого «итогового счёта» или объяснимого рейтинга сравнения;
- нет фильтрации по важности клиента;
- нет режима «только подтверждённые отличия»;
- нет сохранения/истории сравнений;
- нет экспорта в PDF/ссылку/CRM;
- нет сравнения больше двух компаний;
- нет отображения даты/версии конкретного документа рядом с условием;
- нет явного CTA после результата: отправить клиенту, сохранить, запросить консультацию.

### P1 — слабая эксплуатационная прозрачность

`/health` проверяет наличие snapshot и число компаний, но не проверяет:

- свежесть каждого источника;
- число просроченных документов;
- наличие критических ошибок последнего сбора;
- статус базы данных;
- готовность AI-провайдера;
- расхождение между последним запуском и опубликованными данными.

Для ежедневного сбора нужен health/readiness endpoint с понятными статусами и алертом.

### P1 — зависимости не установлены в текущем окружении, тесты не запускаются полностью

`python3 -m compileall` проходит успешно, но полный `unittest` сейчас не проходит из-за отсутствующих зависимостей (`psycopg`, `fitz` и связанных пакетов). Это не доказывает ошибку в коде, но означает, что локальная проверка проекта не воспроизводится без установки `requirements.txt`.

**Рекомендация:** добавить воспроизводимый dev setup:

- `.python-version` или явную версию Python;
- lock-файл (`uv.lock`/`poetry.lock` или pinned requirements);
- `make test`, `make lint`, `make run`;
- отдельные lightweight и CASCO dependencies;
- smoke-test приложения без реальной БД.

### P1 — секреты и внешние провайдеры завязаны на окружение

Сбор использует `DATABASE_URL`, `GROQ_API_KEY`, `GEMINI_API_KEY` и переменные GitHub Actions. Это нормально для production, но сейчас не хватает явной документации по обязательным и необязательным переменным, fallback-поведению и проверке конфигурации до запуска.

Нужна команда/endpoint `config check`, которая не выводит секреты, а показывает только:

- configured / missing;
- provider enabled / disabled;
- DB reachable / unavailable;
- last successful collection.

### P1 — смешаны CASCO и недвижимость без общего продуктового слоя

В коде уже появились `property_*` модели, baseline для RESO и пилот конкурента. Это хороший задел, но UI и основной пользовательский поток пока практически целиком CASCO.

Рекомендуется не добавлять ещё больше полей напрямую в общий шаблон, а ввести product-aware слой:

```text
Product
 ├── scenario/schema
 ├── comparison fields
 ├── evidence rules
 ├── scoring rules
 └── presentation template
```

Тогда CASCO и недвижимость будут разными продуктами на одной платформе сравнения.

## 4. Предлагаемая продуктовая концепция

Наиболее логичное направление по текущему коду:

> **Страховой аналитик — рабочее место агента, которое превращает официальные правила страховых компаний в проверенные аргументы для разговора с клиентом.**

Целевой сценарий:

1. агент выбирает продукт: КАСКО или недвижимость;
2. выбирает свою компанию и 1–3 конкурента;
3. указывает приоритеты клиента: цена, ремонт, франшиза, GAP, сроки, ограничения;
4. получает ранжированные различия с уровнем доказательности;
5. получает готовое сообщение в тоне WhatsApp/email;
6. сохраняет сравнение и делится безопасной ссылкой;
7. видит дату документа и предупреждения об условиях договора;
8. может отправить результат в CRM или экспортировать PDF.

## 5. Приоритетный план работ

### Этап 1 — стабилизация запуска

1. Убрать двусмысленность `app.py` vs `web_app.py`.
2. Привести `Procfile`, Vercel entrypoint и локальный запуск к одному приложению.
3. Сделать явный `DATABASE_URL` startup check.
4. Добавить минимальный smoke-test: `/`, `/health`, `/compare` с mock snapshot.
5. Добавить документацию запуска и переменных окружения.

### Этап 2 — закончить основной B2B-сценарий

1. Авторизация и организации/команды.
2. История сравнений.
3. Сохранение результата как immutable snapshot.
4. Экспорт PDF и копирование короткой ссылки.
5. CTA «Отправить клиенту» с безопасным публичным представлением.
6. Настройка профиля агента: название, подпись, контакты, логотип.
7. Логи использования и базовая аналитика воронки.

### Этап 3 — сделать результат объяснимым и продающим

1. Весовые приоритеты клиента.
2. Рейтинг по каждой категории, а не непрозрачный общий балл.
3. Маркировка: «подтверждено правилами», «зависит от договора», «требует проверки».
4. Показ даты документа/редакции.
5. Режим сравнения 2–4 компаний.
6. Готовые шаблоны сообщений: короткий, подробный, нейтральный.
7. Явный дисклеймер: сравнение не заменяет индивидуальный расчёт и договор.

### Этап 4 — расширение на недвижимость

1. Завершить общий product schema layer.
2. Разделить сценарии apartment/house и их обязательные поля.
3. Добавить competitor registry и coverage dashboard.
4. Не публиковать property-значения без того же evidence quality gate, который уже используется для CASCO.

### Этап 5 — коммерциализация

Для B2B:

- тарифы по числу пользователей/сравнений;
- white-label для агентств;
- CRM/API;
- командные роли и аудит действий.

Для гибридного B2C:

- публичный лид-лендинг;
- форма с данными клиента и автомобиля;
- передача заявки агенту;
- партнёрские ссылки или комиссия;
- согласие на обработку персональных данных.

## 6. Что я бы сделал первым изменением

Если цель — быстро довести текущий проект до полезного продукта, я бы начал не с нового AI-функционала, а с трёх вещей:

1. **Зафиксировал единый production entrypoint.**
2. **Добавил сохранение и отправку результата сравнения клиенту.**
3. **Превратил результат в понятный sales workspace с приоритетами клиента и 2–4 компаниями.**

Именно это даст больше пользовательской ценности, чем ещё один сборщик или ещё один AI-провайдер.

## 7. Рекомендуемая следующая задача

Сформулировать один целевой сценарий в формате:

> «Пользователь X выбирает Y, вводит Z и получает результат W, после чего совершает действие Q».

Например:

> «Страховой агент выбирает РЕСО и конкурента, отмечает, что клиенту важны ремонт у дилера и GAP, получает три подтверждённых аргумента и отправляет клиенту готовое сообщение в WhatsApp».

После выбора сценария можно перейти к конкретному implementation plan с файлами, миграциями БД, API, UI и тестами.
