# Инструкции для ИИ-агентов (Claude Code, Codex и др.)

Проект — «Страховой аналитик»: рабочее место страхового агента для сравнения условий КАСКО
11 страховых компаний по 10 параметрам на основе официальных правил страхования.

## Как устроено

- **Единственное приложение — `web_app.py` (Flask).** На Vercel оно запускается через
  `vercel_db_entry.py`, локально и через `Procfile` — как `web_app:app`. Старого `app.py` больше нет,
  не создавайте его заново.
- **Источник данных для сайта — `data/casco-comparison-master.json`** (принятый набор 110 ячеек:
  11 компаний × 10 параметров). Если файл есть, база данных сайтом не используется.
  База PostgreSQL (`DATABASE_URL`) нужна только для конвейера сбора (`collector/`, `scripts/`).
- **Логика сравнения — `core/services/sales_insights_service.py`.**
  Шаблоны — `templates/`, стили — `static/app.css`.
- **Официальные PDF правил** — `data/sources/<страховщик>/`, ссылки на оригиналы — `docs/source-urls.md`.
- Каждый пуш в `main` автоматически выкатывается в продакшен на Vercel.

## Правила сравнения — единые для всех 10 параметров

1. **Условие прямо указано в официальных правилах только одной компании — это её преимущество.**
   Отсутствие условия в принятом источнике другой компании не делает сравнение «нейтральным».
   Исключение — когда указанное условие является прямым исключением риска: «исключено» у одной
   и «не указано» у другой — это «равно» (у обеих минус), а не преимущество исключившей.
   Решение о том, указано ли условие, принимают структурированные факты (`{поле}_facts`,
   `core/condition_facts.py`); главное утверждение — первое предложение ответа, оговорки его не отменяют.
2. **Условие указано у обеих — сравниваются значения.** Параметр задаёт только *способ чтения значения*
   (таблица `_FIELD_COMPARATORS`): сумма франшизы, порог тотала, срок выплаты, форма ремонта,
   уровень покрытия. Правила принятия решения одинаковы для всех.
3. GAP, самовозгорание, терроризм и БПЛА — «параметры покрытия», читаются одинаково:
   исключено < доп. опция < включено.

Не добавляйте особые правила для отдельного параметра (например, «только для GAP»).
Если нужно новое поведение — сделайте его общим и добавьте тест, что все параметры одной группы
ведут себя одинаково (см. `UnifiedRuleTests` в `tests/test_sales_insights_service.py`).

## Проверка изменений

```bash
pip install -r requirements.txt pytest
python -m pytest -q
```

16 тестов пропускаются без PostgreSQL/Docling — в GitHub Actions они выполняются.

При любом изменении логики сравнения проверьте влияние на все пары компаний:

```bash
python scripts/compare_all_pairs.py /tmp/before.json   # на main
python scripts/compare_all_pairs.py /tmp/after.json    # на вашей ветке
python scripts/compare_all_pairs.py --diff /tmp/before.json /tmp/after.json
```

Каждое изменившееся сравнение должно быть объяснимо; перечислите их в описании PR.

## Порядок работы

- Работайте в отдельной ветке и открывайте pull request в `main`. Сливайте только после зелёных
  проверок GitHub Actions («Python tests», «CASCO document pipeline tests»).
- Пишите описание PR и общение с владельцем проекта на русском языке.
- После каждой правки давайте владельцу пошаговую инструкцию: что нужно сделать на GitHub
  (слить PR, удалить ветку и т.п.) и в настройках Vercel, чтобы изменение заработало на сайте.
- Не коммитьте `__pycache__`, `.env`, PDF в корень репозитория.

## Известные ограничения

- Ежедневный сбор (`daily-collection.yml`) сверяет копию PDF из репозитория, а не свежий файл
  с сайта страховщика, поэтому изменения правил на сайтах он пока не замечает
  (см. `collector/casco_pipeline.py`). Менять это — только по решению владельца.
- Подключение Vercel к ИИ-инструментам пока не видит команду `manager-90-plan`
  (ошибка на стороне Vercel); статус деплоя смотрите через статусы коммитов на GitHub.
